## 固件修正

本机实际使用 Arduino-ESP32 2.0.17。库中 `WiFiClient::write` 含单次约 1 秒的可写等待和多次重试，而本项目启用了循环任务看门狗。这是采样停顿/看门狗复位的可行原因，但旧固件没有保存复位原因，不能确认它解释了所有历史重启。

`imu-body-node-20261027-r4` 的改动：

1. TCP 使用 `MSG_DONTWAIT`，每轮最多执行一次发送，不在采样循环中等待套接字变为可写。
2. 固定 8 × 512 字节帧队列；正确保留部分发送的剩余字节。拥塞导致队列满时关闭整个流并清空队列，让上位机明确观察断线/缺帧，不拼接残缺帧，也不无限积压延迟。
3. USB 硬件 CDC 发送缓冲设为 1,024 字节，整帧空间不足时跳过该 USB 帧并累计统计；诊断写入超时限制为 1 ms。USB 慢读不再通过逐帧等待拖住 Wi-Fi 采样。
4. 串口输出 `[Reset] Reason=...` 与周期 `[Transport] TCPBackpressure=... TCPErrors=... USBSkipped=...`，便于后续区分看门狗、供电和发送拥塞。IMU3 数据列保持兼容。

新增原生队列测试覆盖部分发送、容量耗尽、环形复用、断线清空和调用方缓冲所有权，含 10,000 次固定种子的随机状态验证；MSVC `/W4 /WX` 通过，并已加入 GitHub CI 的 g++ 检查。A/B 两种固件均以项目 `-Wall -Wextra -Werror` 构建通过。

右前臂部署构建：静态 RAM 49,296 / 327,680 字节，程序 727,409 / 1,310,720 字节；静态 RAM 已包含约 4 KiB TCP 队列，USB 缓冲另占运行时堆内存。未测功耗、最坏栈余量或十四板规模。
